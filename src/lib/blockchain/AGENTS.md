# Blockchain module guidance

- Use creatorVaultCustody.ts: never burn/mint; engrave and release before bucket changes. creatorMarketOperation excludes local overlaps; creatorVaultBacking protects payout layers, not peer consensus.
- Use customTokenLimits.ts for caps and ownedAssets.ts for positive balances. Read the market readiness plan before expansion: self-transfers are not escrow; profile reads must not initialize vaults.
- Use coldKey.ts for MintMe withdrawals: key authority is a Creator Coin Vault or a 1-SWARM engraved container; the secp256k1 key is derived from the identity key (never displayed); deposits target the cold-key address; the ledger debits only after the MintMe broadcast succeeds.
- Persist only the public cold-key receiving address in account-scoped metadata at unlock; deposits resolve it independently of signing authority, never substitute display aliases. Announce signup only after authorization is cached, and bind in-memory keys to the active account.
- SWARM Market Vault: pure pricing in marketVaultPricing.ts; marketVault.ts uses the shared operation guard and releases only already-mined pool SWARM, never mints.
- Creator payments use the profile-market spot and recheck it before payment; atomic holder-to-pool ownership updates preserve supply. Refund failed releases only if payout is absent from the ledger, so accepted SWARM is never refunded twice. This is local settlement, not peer consensus.
- Creator market quotes retain their last rate during coalesced market-event reads, not pool ticks; payments automatically use the unlocked identity vault, never substitute session metadata for a signing key.
- Wallet dialogs (transfers, SWARM↔MetaMask, custom-token withdrawals) never prompt for a passphrase; they sign with the unlocked session key and fail closed with a sign-in message when the vault is locked — a session label never substitutes for the key. The unlocked key is also sealed in sessionStorage and on-device under a non-extractable IndexedDB CryptoKey so refreshes and new visits stay authorized until Lock wallet or sign-out; restores only for the signed-in account.
- Direct MintMe custody (no MetaMask): balance-sync deposits credit only cold-address balance + recorded outflow − recorded inflow, rechecked live; withdrawals are signed by the user's cold key, require value plus a fixed MINTME gas hold, and debit value plus actual gas only (so sync never re-credits); the queue stores the tx hash at broadcast and never re-sends — replay cannot query past balances.
- Wallet send/receive is native cold-key only; MetaMask-era records are accepted for history, never created by the UI.
- Content engraving uses the serialized contentPayload writer for appends and manual/idle seals, with cross-tab Web Locks when available; tiers are optional Creator Proof metadata, and loaded containers never enter media reuse or stress-only sealing.
- Engraved entries are NFT-style (v2): metadata plus media pointers (file id, MIME, size, chunk refs, content hash) sized by full file bytes; never copy file keys or raw bytes into a coin. Engraved files are relocated by reference (manifest `_coinId`), never copied; space cleanup and deleteManifest keep them. Only open coins re-engrave legacy or pending-media entries, releasing any that no longer fit; sealed coins are never re-engraved.
- Infinity reflection coins (`infinity/reflectionCoins.ts`) take only hollow pool coins (no tokens, chat, chemicals, payload, vault or seal), always leave POOL_SURPLUS_REQUIREMENT wrappers in the pool, move ownership pool → `infinity` without minting or burning, seal through applySeal and record one coin_transfer per reflection seal.
- The media wrap sweep (`mediaCoinWrapSweep.ts`) engraves only vault files flagged `createdBySelf`; content received from peers stays queued and never spends a wallet coin. Unflagged legacy entries are treated as not self-created.
- Media coins carry bytes only in transit: `mediaCoin.standalone.ts` hands the whole coin (manifest + every verified chunk) to one connected peer at a time, each peer unpacks it, appends itself to `route.hops`, and passes it to an unvisited peer until it returns to `route.creatorId`. At rest, `mediaCoinRuntime.ts` stores the unpacked file once in the regular chunk store and the coin keeps pointers, so the v2 "no raw bytes in a coin" rule still holds for stored coins. Decryption keys ride only direct hand-offs, never broadcasts. Files over `MEDIA_COIN_PASS_MAX_BYTES` stay torrent-only.
- A coin launched from a post's file carries a torrent binding (file id, signed manifest, per-chunk IVs and sizes; hand-offs only, like the key). On arrival `mediaCoinTorrentFill.ts` checks the local manifest (or saves the carried one if its signature verifies), counts chunks already present, and rebuilds only the missing ones by re-encrypting the coin's slice with the file key and that chunk's IV, storing it only when its ref matches the manifest. Flushed files stay flushed. A completed fill enrolls the vault with the post's file id (no second copy) and the mesh seeds it; a coin with no usable binding falls back to storing its own copy.
- MintMe miner startup must check getMintMeMinerEnabled() in src/lib/mining/mintmeMinerPreference.ts — the dashboard switch is the single gate.
- MintMe controller uses public community receiving configuration only, waits for a verified bundled engine before pool connection, and treats unsigned mesh receipts as advisory, never payout authorization; user keys and CryptoNight assumptions cannot establish MintMe settlement.
- MintMe community rounds (communityPayoutService): 30-min heartbeat, own pool read, strict majority (min. two) or 2-hop tie-break; numbered rounds prevent double pay. On-chain, peers cold-key-sign attestations (mintmeMiner/rewardContract.ts) verified by the external Reward Contract via ecrecover; autoClaim.ts claims while unlocked — no pool/Infinity key exists.
- One native MINTME balance: custody deposits, signed tips and verified round records (labelled by mintMeSource); MintMe withdrawals go through mintmeWithdrawQueue (peer-gated, queued, reversed on failure; contract release stays queued until deployed — never simulated).
- MintMeMiningService owns the app-wide worker lifecycle; the isolated mining Gun registry discovers credential-free public WSS bridges only from live mesh neighbours matching configured custody. Browsers advertise external bridges, never host them; keep mining independent of Brain, native mining and Global Cell dialing.
- MintMe hashing uses pinned upstream Lyra2v2-Webchain C compiled to public/wasm and fetched by URL only in the post-hydration client worker, never source-imported (server bundling breaks deployment); self-test before connection, hash full blobs with eight-byte tail nonces and bounded slices because generic Lyra2REv2/CryptoNight layouts are incompatible.
- Cell chains (cellChain/): each private cell is its own chain and coin (ticker from the cell name) under the shared chain's rules (PoW, v2 header, 30s beats, 95/5, 20-block maturity, chain-derived voters, checkpoints). Roster records and member-to-member transfers ride in blocks and take the block's time. Sync runs over the cell engine to proven members and invitees only. Miners on both chains start from their spot on the golden-ratio manifold (manifold.ts), a production rule and not a validation rule. Wallet > Chain lists a cell chain for its creator always, and for members once the roster has two or more (cellWallet.ts).
- Chain storage is one IndexedDB record per block (`block-<index>`) plus a small `chain-state` record holding `chainLength`; `persistState` writes only blocks whose hash changed since the last save and deletes stored blocks past a shorter adopted chain in the same transaction. Never put the whole chain in one record or in the localStorage tab-hide snapshot (that snapshot is v2: pending transactions plus unstored tail). Ledger walks over the chain resume from a cached state keyed by a block hash rather than re-walking from genesis per block.
